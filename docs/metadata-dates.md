# 既存日時の確認

2026年10月21日に`akua-server`のv3.3.0.2を読み取り専用で確認しました。サーバー設定は`TZ=Asia/Tokyo`で、撮影日時がない画像へのパッチも適用されています。

## 表示と保存値

Immichは実時刻を`asset.fileCreatedAt`と`asset_exif.dateTimeOriginal`に、タイムラインの日付分けに使う壁時計時刻を`asset.localDateTime`に保存します。詳細表示は撮影日時と`asset_exif.timeZone`を使います。今回の変更では、この既存の形式を維持します。

タイムゾーンがない撮影日時をUTCとして解釈すると、日本のカメラ写真と実時刻の基準が9時間異なります。タイムラインの日付分けと一覧の並び順はそれぞれ壁時計時刻と実時刻を使うため、両方の保存値を正しく扱う必要があります。

## 以前の一括修正

10月6日の計画は77,618件を確認し、19,069件の修正を提案しています。78分割すべてに適用記録があります。修正済み60件の標本では、現在もzone付きの撮影日時とタイムライン用日時が一致しました。

最初の1,000候補では252件を修正対象とし、748件を除外していました。そのうち732件は、保存時刻と現在のファイルの作成・更新日時が一致しないため除外しています。この数は最初の分割だけの結果であり、全体の内訳ではありません。

## 補正ツールの対象範囲

既存の`runtime/metadata-date-repair`は、撮影日時がなく、保存時刻を現在のファイル日時でも確認できるPNG/JPEGを対象に、`localDateTime`と`timeZone`だけを補正します。撮影日時がある画像、sidecarや日時ロックがある画像、保存時刻の根拠が一致しない画像は除外します。

今回、新しい棚卸しスクリプトや自動補正処理は追加していません。既存の計画・適用記録で過去の修正範囲を確認できます。一方、その記録には後から追加した画像は含まれず、除外された画像の正しい日時も確定できません。今回の対象数を確定するには、該当画像のIDと元メタデータ・保存値の照合が必要です。

棚卸しに使う既存の入口は[`Repair-MetadataDates.cmd`](../runtime/metadata-date-repair/Repair-MetadataDates.cmd)です。実体は`Repair-MetadataDates.ps1`と`cli.cjs`の`plan-all`です。画面でユーザーを選ぶと読み取り専用の計画を作り、適用の確認で`0`を選べばDBは変更しません。候補ごとの除外理由は保存した計画ファイルに記録されます。これは現行補正ツールの対象候補を調べる処理で、撮影日時がある画像を含む全種類の日時不具合を検出するものではありません。

棚卸しを中断した場合は、同じ入口の再開を選び、直前の修復フォルダーを指定します。1,000候補ごとに保存した計画を再利用し、その先から読み取ります。保存途中だった分割は読み直します。別バージョンへの更新、DB・ユーザー・タイムゾーン・実行ファイルの変更があれば、以前の計画は再利用しません。

DBへの適用は1画像ずつ確定します。適用中断後の自動継続はありません。`reconcile`で記録とDBを照合し、不確定な書き込みを確認してから、残った候補の新しい計画を作ります。棚卸しの再開と適用の再開は区別してください。

元画像全体のSHA-256は計算しません。計算するのは6個のサーバーファイル、5個の補正ツールファイル、計画ファイル、対象から抽出した少数のメタデータなどです。用途は同じ処理・同じ計画での再開と、適用前の変更検出です。ファイルそのもののハッシュとJSONの内容ハッシュは役割が異なります。再開検証で同じJSONの内容ハッシュを2回計算していた箇所は1回に減らしました。

更新だけでは既存データは変わりません。撮影日時がある画像は新しい抽出処理で再計算できますが、通常のメタデータ更新は日時以外も処理するため、ライブラリ全体には実行していません。旧ツールの除外条件を緩めたり、すべてのスクショに9時間を加算したりする変更も行っていません。

## 配布バージョン

`upstream.json`の`version`と`commit`は上流Immichの固定元です。`windowsRevision`がWindows独自の改訂番号で、配布版は`version.windowsRevision`になります。今回の準備版は上流v3.3.0を維持したv3.3.0.4です。サーバーで確認した版はv3.3.0.2、修正前のリポジトリはv3.3.0.3でした。

パッチは既存のソース準備とアプリのキャッシュキーに含まれます。公開済み版の配布内容を変更した場合は同じ版を再公開できず、改訂番号の更新が必要です。上流自動更新は新しい上流版の改訂番号0から始まります。今回、公開・サーバー更新・既存データの変更は行っていません。

補正ツール自身に上流コミットやバージョンの固定値を重複して持たせず、配布物のmanifest・依存関係の由来情報・サーバーのpackage.jsonが一致することを確認します。その上で実際の日時メソッド・DBスキーマ・トリガーを検証するため、新しい上流版の自動検証も同じ経路で実行します。
